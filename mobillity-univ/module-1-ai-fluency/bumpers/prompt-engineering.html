Prompt Engineering: How You Ask Changes What You Get

Mobillity EIT Urban Mobility Co-funded by the European Union

You already prompt language models every day. So it is tempting to treat "prompt engineering" as a repackaging of something you have covered. It isn't. There is a measurable gap between a casual prompt and an engineered one, and in data analysis that gap decides something concrete: whether the Python the model writes for you is correct, or confidently wrong.

Remember the lesson from when casual prompting fails: the fix was never a cleverer question typed into the chat box. It was changing how you direct the model — asking it to write code that processes every row and computes the real numbers, instead of asking it to be the analysis engine and hand you an answer it may have made up. This guide is about that skill, generalised: how to brief the model so it does the job well. The model writes the code. You own how well it is briefed.

1. What is prompt engineering?

Prompt engineering is the craft of structuring your instructions so the model reliably does what you want — how you phrase the request, what context you include, and what shape of output you ask for. Anthropic puts it plainly: it is "how you phrase queries, specify style, provide context, and guide the model's behavior to achieve your goals."

A useful way to picture it, borrowed from Anthropic's own guidance: treat the model like a brilliant but brand-new colleague. It is fast and widely read, but it has never seen your dataset, doesn't know your definitions, and cannot tell what "good" looks like to you unless you say so. Their golden rule is a good test — if you handed your prompt to a colleague with no context and they'd be confused, the model will be too.

Here is the difference on a mobility task. Suppose you have a bus timetable feed and want to find weak routes.

A casual prompt:

Analyse this bus data and tell me which routes are underperforming.

An engineered prompt:

You are a transit data analyst. I have a GTFS feed as a pandas DataFrame `trips`
with columns: route_id, trip_id, service_id, departure_time (HH:MM:SS, can exceed
24:00), stop_count.

"Underperforming" means a route whose average daily trip count is in the bottom
quartile AND whose average stop_count is below the network median.

Write pandas code that computes this, prints the flagged route_ids with their two
metrics, and adds one sentence explaining each flag. Do not invent columns — if you
need one that isn't listed, say so instead of assuming.

The second prompt wins not because it is longer, but because it removes guesswork. The casual version forces the model to invent a definition of "underperforming," guess your column names, and decide on its own whether you wanted prose or code — three places it can quietly go wrong. The engineered version answers those questions up front, so the model spends its effort on the analysis instead of on mind-reading.

Key idea

Prompt engineering is not about magic words. It is about removing the guesswork — telling the model the things it cannot know but needs in order to be right.

2. Why does it help? The evidence

This is not folklore. The effect of how you prompt has been measured repeatedly in peer-reviewed work, and the effects can be large.

  • Asking the model to reason step by step changes accuracy. Wei et al. (2022) showed that "chain-of-thought" prompting — giving a few worked examples that spell out the reasoning — let a 540-billion-parameter model reach then-state-of-the-art accuracy on the GSM8K math-word-problem benchmark, beating a specially fine-tuned model that had a separate answer-checking model bolted on. Kojima et al. (2022) went further: with no worked examples at all, simply appending the phrase "Let's think step by step" raised accuracy on one benchmark from 17.7% to 78.7%, and on GSM8K from 10.4% to 40.7% (their paper is literally titled "Large Language Models are Zero-Shot Reasoners").
  • Showing beats telling. Brown et al. (2020), the GPT-3 paper, established in-context "few-shot" learning: include a handful of input→output examples in the prompt and the model picks up the pattern and applies it to a new case — no retraining required.
  • The same content, presented differently, gives different results. This is the flip side, and it is why deliberate structuring matters. Lu et al. (2022) found that merely reordering the few-shot examples could swing performance "between near state-of-the-art and random guess." Sclar et al. (2024) found that trivial formatting changes — spacing, separators, punctuation that don't change the meaning — moved accuracy by up to 76 points on one open model.

Two honest caveats keep this in proportion. First, these are early findings on the models of their day: modern chat and reasoning-tuned models often already reason step by step by default, so the size of the "magic phrase" effect has shrunk — but the underlying result, that how you structure a request changes accuracy, still holds. (That shrinkage previews section 4's point — prompting guidance itself dates, which is why you check what's current.) Second, the sensitivity findings cut both ways — a single phrasing is not "the" answer. Mizrahi et al. (2024) argue that evaluating a model on one prompt is unreliable and you should try several. So the durable posture is: engineer the prompt, then verify the output — the same verification discipline this course returns to again and again.

Key idea

The takeaway is not "there is one magic prompt." It is that how you ask has a large, measurable effect — so it is worth doing on purpose, and worth checking.

When it's worth the effort

In fairness, the models have got good enough that for many everyday requests a plain, clear prompt is already enough — heavy prompt engineering changes little. Where it earns its keep is the harder cases: when you're optimising for quality or consistency, systematising a prompt you'll reuse many times, or rescuing a task where a simple prompt visibly failed. Spend the effort there, not on every message.

3. The best practices all three providers agree on

Anthropic, OpenAI, and Google each publish official prompting guidance. They use different words, but strip the wording away and the same seven practices appear in all three. Because they are the common ground of every major provider, they are the safe, durable bets — learn these first. Here is the same advice under each provider's own heading:

PracticeAnthropic calls itOpenAI calls itGoogle (Gemini) calls it
1. Be explicit and specific"Be clear and direct""Instructions""Clear and specific instructions"
2. Give context and the reason"Add context to improve performance""Include relevant context information""Add context"
3. Show a few examples"Use examples effectively""Few-shot learning""Zero-shot vs few-shot prompts"
4. Specify the output format"Control the output format""Structured Outputs""Response format"
5. Separate the parts with structure"Structure prompts with XML tags""Message formatting with Markdown and XML""Consistent formatting"
6. Break complex tasks into steps"Prompt chaining"Decompose into sub-requests"Break down prompts into components"
7. Give the model a role"Give Claude a role""Identity""role definitions (persona)"
  1. Be explicit and specific. State the task, the constraints, and what "done" looks like; don't rely on the model to infer them.
    → Instead of "summarise this survey," write "summarise this rider-satisfaction survey in five bullet points, one per service line, each with the mean score."
  2. Give context and the reason why. Tell the model the purpose and the audience — every provider notes the model generalises better when it understands why.
    → "This is for a transport authority deciding evening service, so weight recent months more heavily."
  3. Show a few examples (few-shot). Demonstrate the format or judgement you want with one to a handful of examples. Google is blunt: "We recommend to always include few-shot examples."
    → Label one flagged route as service gap the way you would categorise it, then ask the model to classify the rest of the routes the same way.
  4. Specify the output format. Ask for the exact shape — a table, a JSON object, a code block, a one-paragraph answer — so you don't burn a turn reformatting free-form text into the table or JSON you actually needed.
    → "Return a table with columns station_id, missing_pct, and a recommendation."
  5. Separate the parts of your prompt with structure. When a prompt mixes instructions, data, and examples, mark the boundaries — with headings or with descriptive XML-style tags like <csv data>...</csv data> — so the model doesn't mistake one for another.
    → Wrap a pasted CSV in <csv data> tags so the model never reads a data value as an instruction.
  6. Break complex tasks into steps. For anything multi-stage, lay out the steps in order or split the work into a chain where each output feeds the next — because cramming a multi-stage analysis into one instruction is exactly where a model blends or skips steps.
    → "First list the cleaning steps this GTFS feed needs. Then, once I confirm, write the code for step one."
  7. Give the model a role. A sentence naming who the model should act as focuses its tone, priorities, and defaults — even one line makes a measurable difference.
    → Open with "You are a transit data analyst" so the model frames the whole task the way a domain expert would.
Key idea

These are not a script to memorise. They are the questions to answer before you press enter: What exactly do I want? Why? Who should the model act as? Can I show an example? What format? Are the parts clearly separated? Is this one step or several?

4. Where to get the best guidelines

Here is the catch that trips people up: best practices move. Models change, and a prompt tuned for last year's model can actively hurt on this year's. This is not speculation — it is written into the providers' own docs.

A concrete case. For older models, a widely shared best practice was to spell out every rule you wanted — a long, defensive rulebook of "always do this, never do that." Anthropic's guidance for its newest model, Claude Fable 5, partly reverses that: because the model's instruction-following improved, "you can steer most behaviors with a brief instruction rather than enumerating each behavior by name," and a short instruction "is as effective as listing each pattern." The same page warns that prompts "developed for prior models are often too prescriptive… and can degrade output quality." So the old long rulebook is not just unnecessary now — it can make results worse. Watch the same cleaning task age:

Written for an older model (the long rulebook):

Clean this GTFS feed. Follow these rules exactly:
1. Drop rows with missing departure_time.
2. Do NOT drop rows for missing stop_name.
3. Convert departure_time values over 24:00:00 to valid times.
4. Do NOT modify route_id.
5. Do NOT add any columns.
6. Do NOT summarise the result.
7. Return only the cleaned DataFrame and nothing else.

Rewritten for the current model (per its own guidance):

Clean this GTFS feed so it's ready for a stop-frequency analysis. Keep changes
minimal: fix departure_time values over 24:00:00 and drop rows with no
departure_time, but don't restructure anything else. If a choice isn't obvious,
ask me instead of guessing.

Same task, shorter prompt, and it trusts the model's improved instruction-following instead of fighting it. This is why the durable skill is not memorising a fixed list of tricks — it is knowing where the current guidance lives, and reading it before a big or repeated task. Each provider keeps a living guide and even publishes model-specific pages:

  • Anthropic: the prompt-engineering overview and the "Prompting best practices" reference, plus per-model pages. https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview
  • OpenAI: the prompt-engineering guide, with a dedicated "latest model" best-practices page. https://developers.openai.com/api/docs/guides/prompt-engineering
  • Google (Gemini): the "Prompt design strategies" guide. https://ai.google.dev/gemini-api/docs/prompting-strategies

(This even loops back to section 2: remember the "Let's think step by step" finding? Many current reasoning models already do that by default, so asking for it explicitly can now be redundant — exactly the kind of thing the current guide will tell you.)

Try this

Before a big or repeated task, spend ten minutes on the current guide for the model you are actually using. It routinely changes what you decide to ask for.

5. Metaprompting: let the model write the prompt

You don't have to write the perfect prompt alone. Metaprompting is asking the model to write or improve a prompt for you — pointing the model at the task of prompting itself.

Why does this work? Three honest reasons, two of them backed by research:

  • Models are trained on enormous amounts of instructions, documentation, examples, and tutorials, so they have absorbed what good prompts tend to look like. Zhou et al. (2022) showed that instructions generated by an LLM matched or beat human-written prompts on most of the tasks they tested — the paper is titled, only half-jokingly, "Large Language Models Are Human-Level Prompt Engineers."
  • A model can critique text and rewrite it, so it can run the same generate → critique → improve loop on a prompt that a human editor would.
  • Practically, a prompt is something you can read, edit, and re-run instantly — there is no training loop involved, so trial-and-error is cheap and the result is right there for you to inspect.

One important limit: metaprompting works within the model's ceiling. It makes a solvable task easier to get right; it cannot make the model capable of something it fundamentally can't do. And because of the sensitivity you saw in section 2, always test the improved prompt rather than assuming it is better.

Here is the loop on a mobility task.

Your rough prompt:

Analyse the bus route and tell me which stops are inefficient.

Your metaprompt (ask the model to improve it):

Improve the prompt below so a data analyst gets a reliable answer. Make it: define
what "inefficient" means operationally, state the input columns, break the analysis
into steps, and specify a structured output. Ask me for anything you need.

Prompt: "Analyse the bus route and tell me which stops are inefficient."

What comes back is a far stronger prompt — something like:

You are a transit operations analyst. Given a CSV with columns stop_id, stop_name,
dwell_time_min, passengers_per_hour, distance_to_next_stop_km, identify inefficient
stops.

Flag a stop if any hold: passengers_per_hour < 5, dwell_time_min > 2, or
distance_to_next_stop_km < 0.5.

Steps: (1) compute the mean of each metric across all stops; (2) flag stops crossing
any threshold; (3) for each flagged stop, name the triggering metric and compare it
to the route mean; (4) recommend consolidate / skip / investigate.

Return JSON: a route summary, then one object per flagged stop with its metrics and
recommendation.

You just skipped the hard part of writing all that yourself. Providers ship this as a button: Anthropic's Console has a prompt generator and prompt improver; OpenAI has a Generate feature; Google offers a prompt optimizer in Vertex AI.

Try this

Paste your rough prompt and say: "Improve this prompt for [task], and ask me for anything you need to make it precise." Answer its questions — that back-and-forth is where the quality comes from.

6. Metaprompting with the current best practices

Metaprompting has one weakness: the model rewrites your prompt using whatever it learned during training — which may predate the current guidance entirely. A model released last year never saw this year's best-practices page. You close that gap by combining section 5 with section 4: point the model at the current guidance and have it rewrite your prompt to match. The most direct way is to give it the link to the guideline page for the exact model you're using — the same URLs from section 4.

Take the improved bus-stop prompt from section 5 and hand the model the live page:

Rewrite the prompt below to follow the current best practices for Claude Fable 5,
described here:
https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5

Prompt: "[the improved bus-stop prompt from section 5]"

Because the model reads the page at the moment you ask, it can apply advice that did not even exist when it was trained — which is the whole point. If your interface can't open links, paste the key points into a <guidance> block instead; same idea, done by hand:

Here is current guidance for the model I'm using:
<guidance>
- Give the reason, not only the request: say what the analysis is for.
- Trust the model's instruction-following: a brief, clear instruction beats a long
  rulebook, and over-prescriptive prompts can degrade output.
- Give the model explicit permission to say when it's unsure instead of guessing.
</guidance>

Rewrite the prompt below to follow that guidance, for Claude Fable 5.
Prompt: "[the improved bus-stop prompt from section 5]"

Either way, notice how the result differs from the plain rewrite in section 5. It adds the intent the guidance asks for, loosens the rigid rulebook the guidance warns against, and builds in the permission-to-be-uncertain that reduces made-up answers:

You are a transit operations analyst. I'm reviewing this route for a transport
authority deciding which stops to consolidate, so the goal is defensible flags, not a
long list.

From the CSV (stop_id, stop_name, dwell_time_min, passengers_per_hour,
distance_to_next_stop_km), find stops that are weak on ridership, dwell time, or
spacing relative to the rest of the route. Use your judgement on thresholds and state
the ones you used. For each flagged stop, give the evidence and a recommendation.

If the data is too thin to judge a stop, say so rather than guessing.

Two things to notice. It drops section 5's numbered steps — with a model that reasons well by default (section 2), you don't have to dictate the decomposition, though for a weaker model you'd keep section 3's explicit steps. And loosening the thresholds isn't undoing "be specific" from section 3: the model still has to state the thresholds it used, so it isn't guessing — you're just not hand-coding the numbers.

You are now pairing the model's fluency with the provider's up-to-date, model-specific advice, instead of trusting the model's training-time memory of what "good prompting" means — and, as always, you test the result on a real case before relying on it.

Try this

Take a draft prompt and add one line: "follow the current best practices at [paste the guideline URL for your model from section 4]." If your tool can't open links, paste a few lines from the guide into a <guidance> block instead. Then compare the result against the version you'd have written without it.

7. Keep a prompt library

One last habit, and it is the one that compounds. When a prompt works well, save it.

In practice you reuse the same handful of prompt shapes constantly: load a GTFS feed and report its structure, profile a bike-share trip log, plot a distribution of survey responses, sanity-check a route metric against the raw trip data. Rewriting those from memory each time is wasted effort, and it makes your work inconsistent — slightly different every session.

Why a library matters: consistency across your work, reuse instead of rework, easy sharing with classmates or a team, and — importantly — versioning, so when a prompt suddenly stops giving good results you can see what changed. This isn't a niche idea: Anthropic frames its prompt-template tooling around exactly consistency and version control, and OpenAI's guide now recommends you "version prompts in code," with review and tests, like any other part of a project.

If you want ready-made inspiration or heavier tooling, these exist:

  • Anthropic's Prompt Library — a public collection of tested prompts. https://docs.anthropic.com/claude/prompt-library
  • OpenAI Cookbook — worked examples and prompt recipes. https://cookbook.openai.com
  • Prompt-management tools for teams — LangSmith / LangChain Hub, PromptLayer, Humanloop — which add storage, versioning, sharing, and testing.

But you do not need any paid tool to start. A lightweight personal library is enough:

  • Keep one Markdown file (or a small Git repo) grouped by task — loading, cleaning, plotting, checking.
  • One entry per prompt: a short title, the prompt itself with {{placeholders}} for the parts that change (like {{filename}} or {{columns}}), when to use it, and a one-line note on what worked or what to watch for.
  • Track it with Git so you can roll back when an edit makes a prompt worse.
Try this

Next time a prompt gives you a genuinely good result, don't just move on. Copy it into a prompts.md file with a title and a placeholder or two. In a month you'll have a personal toolkit worth more than any generic template pack.

The one thing to remember

Prompt engineering is directing, not guessing. The specific tricks will keep changing — that is why section 4 matters — but the habit won't: be explicit, give context and a format, show an example, read the current guidance for your model, let the model help you write the prompt, check that draft against today's guidance, and keep the prompts that work. The model writes the code; you are responsible for how well it's briefed. And then — every time — you verify what it produced.
